# Lumi — план реализации принятого направления

Основа: [SPEC.md](SPEC.md), решения пользователя от 16.11.2026.
Этапы ниже — инженерное предложение. Они не означают, что функции уже реализованы.

## 1. Отделить библиотеку от старого слоя знания — выполнено

Встроенные воркеры, слой фактов/позиций и мигратор удалены. Основные команды и
`library` используют один парсер и индекс; `init` создаёт современную структуру.
Старые записи в исследовательских проектах сохраняются, но CLI их не обслуживает.
Регрессии чтения, цитирования и сохранности файлов проверяются тестами и на копии диплома.

## 2. Сделать контракт инструмента для агента

Для основных операций определить JSON-результаты: найденное, основание, ошибки, частичный
результат и возможность продолжить. Коды возврата должны отражать результат операции.
Короткий skill уже описывает поиск с нуля, дополнение имеющейся библиотеки и чтение одной статьи.
Инструкции не требуют «ветвей» от пользователя и не навязывают полный проход каждому вопросу.

Готово, когда агент может различить успех/ошибку/частичный результат и восстановиться после сбоя.

## 3. Обеспечить итеративный поиск и надёжное чтение

Пагинация запросов и сохранение результатов при ошибке следующей страницы реализованы.
Новые записи журнала сохраняют ID всех возвращённых результатов, включая повторные находки,
с запросом, провайдером, вопросом и временем. Далее проверить коннекторы живыми запросами,
добавить сохраняемую очередь, связи нескольких поколений и продолжение после прерывания. Масштаб определяет вызывающий агент;
универсальных численных потолков нет. Учёт квот и ограничений провайдеров остаётся явным.
Методы сходства списков ссылок оценивать по полезным находкам, не добавлять ради количества методов.

Проверить скачивание, извлечение по страницам и OCR для EN/ZH/RU. Сохранять оригинал,
статусы качества и причины неполноты. Чтение и проверка цитат не должны зависеть от claims/beliefs.

## 4. Провести бенчмарк на дипломе

Предложить конкретный исследовательский вопрос обычными словами и согласовать критерий
полезности. Сопоставить новые находки с уже собранной библиотекой; отдельно проверить сбор
с нуля, точечный вопрос и чтение скана. Фикстуры проверяют механизм, живой пилот — пользу.
Число тематических групп не является самостоятельным решением пользователя о качестве.

Пока не выбраны контрольный вопрос/работы (P7) и порядок отдельных эвристик (O5).
Это не отменяет принятый фокус. Режим данных, его пробы, GUI и собственный runtime в этапы не входят.
